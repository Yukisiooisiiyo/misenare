# 本番に出すまでの手引き

このファイルは「どう置くか」の案内です。ここに書いてあることを実行しても、勝手に課金は始まりません。
実際に作るかどうかは、読んだうえで自分で決めてください。

---

## 1. 必要なもの

| もの | 何に使うか | 無いとどうなるか |
| --- | --- | --- |
| PostgreSQL 16 以上 | すべてのデータ | 動かない |
| Node.js 22 以上（または Docker） | API と Web 版の配信 | 動かない |
| 置き場所（サーバー1台） | 上の2つを動かす | 動かない |
| 写真の置き場所 | ナレッジに付ける写真 | サーバーのディスクに置かれる（台を増やすと見えなくなる） |
| HTTPS の証明書 | スマホからの通信 | カメラ（バーコード読み取り）が使えない |

**HTTPS は必須**です。ブラウザはカメラを HTTPS でしか使わせません。

---

## 2. 環境変数

`.env.example` が一覧です。本番で必ず見直すもの：

| 変数 | 既定 | 本番での目安 |
| --- | --- | --- |
| `DATABASE_URL` | なし（必須） | アプリ専用のロールで。**スーパーユーザーは使わない** |
| `PORT` | 8787 | ロードバランサーに合わせる |
| `DB_DRIVER` | `pg` | `pg` のまま（`psql` は開発用） |
| `TRUST_PROXY` | `0` | ロードバランサーの後ろなら `1` |
| `PHOTO_DIR` | `./var/photos` | S3 を使わないときの置き場所 |
| `S3_BUCKET` ほか | なし | 台を2つ以上にするなら設定する |
| `PHOTO_ORIGIN` | なし | S3 を使うときに、そのバケットの URL |
| `TOKENIZER` | `Intl.Segmenter` | `kuromoji`（`npm install kuromoji` が要る。読みが取れて検索が良くなる） |
| `RATE_LIMIT` | `memory` | 台を2つ以上にするなら `db`（PostgreSQL で数える） |
| `MISENARE_RATE_SALT` | 空 | 接続元の IP をハッシュにする鍵。全台で同じ値にする |
| `METRICS_TOKEN` | なし | `/metrics` の合言葉。**本番では必ず設定する** |
| `ALERT_WEBHOOK_URL` | なし | エラーを知らせる先（Slack 互換） |
| `MISENARE_DEV_AUTH` | なし | **本番では絶対に設定しない**（認証をヘッダーだけにする開発用の仕組み） |
| `APP_URL` | `http://localhost:8787` | 招待リンクの宛先。**https のドメイン**。間違うと誰も入れない |
| `WEBAUTHN_RP_ID` | なし | パスキーを使うなら。**ドメイン名だけ**（`https://` やポートは付けない） |
| `WEBAUTHN_ORIGINS` | `https://<RP_ID>` | 受け付ける出どころ。`WEBAUTHN_RP_ID` のドメインである必要がある |
| `WEBAUTHN_REQUIRE_UV` | `1` | 指紋・顔・画面ロックでの確認を必須にする。`0` で緩める |
| `SSO_REDIRECT_URI` | なし | 会社のアカウントを使うなら。`https://<ドメイン>/api/auth/sso/callback` |
| `CONFIG_CHECK` | なし | `off` で起動時の設定の点検を飛ばす（手元で試すときだけ） |
| `SMTP_HOST` ほか | なし | 知らせのメールを送るなら（10 節） |
| `MAIL_FROM` | なし | 差出人。`SMTP_HOST` とこれの両方で初めて送る |

入口（パスキー・SSO）の3つは、**ドメインが決まってからでないと決められません**。
決めなければその入口が閉じているだけで、招待QRでは使えます。4 節の順番を見てください。

### データベースのロール

アプリは行レベルセキュリティ（会社ごとの仕切り）に守りを任せています。
スーパーユーザーや `BYPASSRLS` を持つロールで接続すると仕切りが効かないので、**起動時に確かめて、該当すれば止まります**。

```sql
CREATE ROLE misenare LOGIN PASSWORD '……' NOSUPERUSER NOBYPASSRLS;
CREATE DATABASE misenare OWNER misenare;
```

## 3. 置き方

### 3-1. まずは1台で（おすすめ）

店舗数が少ないうちは、サーバー1台とデータベース1つで十分です。

```
[スマホ] --HTTPS--> [サーバー1台：API + Web版] --> [PostgreSQL]
                            └─ 写真はそのサーバーのディスク（PHOTO_DIR）
```

- Docker があるなら `docker compose up -d` がそのまま使えます（`docker-compose.yml`）。
  これは**手元で動かす用**です。人に見せるところに置くなら `deploy/` のほう（12章）を使ってください。
- HTTPS は Caddy や nginx + Let's Encrypt を前に置くのが簡単です（`deploy/` には設定済みのものが入っています）。
- **この構成で一番大事なのはバックアップです**（下の5章）。

費用の目安：小さなサーバー1台とマネージドな PostgreSQL で、月に数千円〜1万円台。
アクセス量で値段が動く部分がほとんどないので、読み通りに収まります。

### 3-2. AWS に置く場合

従量課金が読みにくくならない組み合わせにしています。

```
[スマホ] → ALB（HTTPS） → ECS Fargate（このイメージ） → RDS for PostgreSQL
                                   └→ S3（写真。端末から直接やり取りする）
```

| サービス | 役割 | 設定のポイント |
| --- | --- | --- |
| ECR | イメージの置き場所 | `docker build` して push する |
| ECS Fargate | アプリを動かす | 0.25〜0.5 vCPU / 1GB から。タスク数は1でよい |
| ALB | HTTPS と振り分け | ヘルスチェックは `/health`。`TRUST_PROXY=1` にする |
| RDS PostgreSQL 16 | データ | db.t4g.micro から。自動バックアップを有効に |
| S3 | 写真 | バケットは**非公開**のまま。アプリが署名付きURLを作る |
| Secrets Manager | 接続文字列・鍵 | 環境変数に直接書かない |
| EventBridge Scheduler | 夜間バッチ | 1日1回、下のコマンドを ECS タスクとして動かす |

**S3 の CORS**（端末から直接アップロードするため）:

```json
[{
  "AllowedOrigins": ["https://<アプリのドメイン>"],
  "AllowedMethods": ["GET", "PUT"],
  "AllowedHeaders": ["content-type"],
  "ExposeHeaders": [],
  "MaxAgeSeconds": 3000
}]
```

S3 を使うときは `PHOTO_ORIGIN=https://<バケット>.s3.<リージョン>.amazonaws.com` も設定します
（Web 版が写真を読み込める先として許可するため）。

**IAM**：タスクロールには、そのバケットへの `s3:GetObject` `s3:PutObject` `s3:DeleteObject` だけを与えます。

費用の目安：Fargate 1タスク常時 + db.t4g.micro + ALB で、月におよそ 7,000〜15,000円。
このうち ALB と RDS が大半で、アクセスが増えても急には増えません。
写真は S3 の保存量ぶんだけ（1店舗あたり数百MB想定なら、月に数十円）。

### 3-3. もっと安く済ませたい場合

- ALB を使わず、Fargate に直接ドメインを向けるのは面倒なので、**Lightsail のコンテナ**か**小さな VPS 1台**のほうが安く簡単です。
- その場合も PostgreSQL はマネージド（バックアップ付き）にするか、自分で毎日バックアップを取ってください。
- **VPS 1台で動かす一式は `deploy/` にあります**（HTTPS 自動取得・夜間バッチ付き）。手順は下の12章です。
  無料枠で試したいだけなら、そこに Oracle Cloud の Always Free での注意も書いてあります。

## 4. 出すまでの手順

**順番が決まっています。** ドメインが決まる前に決められない設定（パスキー・SSO）が
あるので、先に出して、あとから入口を開けます。

| 順 | すること | これが無いと |
| --- | --- | --- |
| 1 | ドメインと証明書を用意する | 以降が全部決まらない |
| 2 | `APP_URL` を決めて出す（招待QRだけ動く） | 招待リンクが localhost になる |
| 3 | `WEBAUTHN_RP_ID` を足して再起動（パスキーが動く） | パスキーの画面が 404 |
| 4 | `SSO_REDIRECT_URI` を足して再起動（会社アカウントが動く） | 会社アカウントの画面が 404 |
| 5 | 本部の管理者が、画面から SSO の設定を入れる | 相手の IdP につながらない |

3 と 4 は**ドメインが決まってからでないと決められません**（パスキーはドメインに
鍵が結びつくため）。2 の時点でも招待QRで使い始められるので、順に開けていけます。

### 設定の点検

起動のときに設定を点検し、足りないものを出します。

```
[設定] × METRICS_TOKEN: /metrics が合言葉なしで見られます
[設定] △ ALERT_WEBHOOK_URL: サーバー側のエラーが誰にも届きません
[設定] ・ SSO_REDIRECT_URI: 会社のアカウントでは入れません（招待QRとパスキーだけで動きます）
```

- **×** は起動しません（黙って壊れるもの）。`CONFIG_CHECK=off` で無視できますが、理由を確かめてからにしてください
- **△** は動きますが、いずれ困るもの
- **・** は「その入口が閉じている」だけ

止めるのを × に絞っているのは、止めすぎると出すのが怖くなって古い版が動き続けるからです。
`NODE_ENV=production` のときだけ × になるものがあります（`APP_URL`、`METRICS_TOKEN` など）。

点検している内容は `apps/api/src/config.ts`、その試験は `apps/api/test/config.test.ts` にあります。

```bash
# 1. イメージを作る
docker build -t misenare:latest .

# 2. マイグレーション（アプリを起動する前に、1回だけ。複数台で同時に流さない）
docker run --rm -e DATABASE_URL=… misenare:latest npx tsx apps/api/src/cli/migrate.ts

# 3. 最初の会社・店舗・管理者を作る（招待リンクが1本だけ出る）
docker run --rm -e DATABASE_URL=… -e APP_URL=https://<ドメイン> \
  misenare:latest npx tsx apps/api/src/cli/bootstrap.ts "会社名" "店舗名" "あなたの名前"

# 4. 起動
docker run -d -p 8787:8787 -e DATABASE_URL=… -e TRUST_PROXY=1 misenare:latest
```

3 で出てくる招待リンクを自分のスマホで開くと、その端末が administrator として登録されます。
あとは画面の「承認・管理 → スタッフを招待する」で、QRコードを見せて増やしていきます。

起動のログに、どの入口が開いているかが出ます。「パスキーが出てこない」と言われたら、まずここを見ます。

```
listening { port: 8787, …, passkeys: 'on', sso: 'off' }
```

### 夜間バッチ（1日1回）

```bash
docker run --rm -e DATABASE_URL=… misenare:latest npx tsx apps/api/src/batch/nightly.ts
```

やること：期限切れのナレッジを外す、タグの関係の候補を作る、索引を作り直す、
タグの使用回数を数え直す、タグの読みを埋める、送りかけの写真を片付ける、
期限切れの合言葉（パスキー）を片付ける。

**タグの読みは、このバッチが「案」を出すだけです。** 検索に効くのは人が確かめた読みだけです。
確認は2か所でできます。

1. **ナレッジを保存した直後**。新しいタグができたら、その場で読みを尋ねます。
   その語を一番よく知っているのは、いま打った人なので、ここが一番当たります。
2. **承認・管理 → タグの読み**。1 で飛ばしたものと、この仕組みより前からあるタグの受け皿。

**信用できない読みは案にしません。** 測定で外したのは、辞書に無い複合語を漢字1文字に
割って読んだものだけでした（食洗機 → ショクアライキ、開梱 → ヒラキコリ）。
そこで「漢字1文字の自立語に割れていない」ものだけを案にします。
間違った案を見せるのは、何も見せないより悪いからです。

**代わりに、漢字の読みの総当たりから候補を5つ出します。** 押すと入力欄に入るだけで、
登録はされません。一文字違いなら、そこから直して登録できます（打ち直すより速い）。

**読みは1つに決めなくてかまいません。** 「下取」は シタドリ とも シタトリ とも
打たれます。どちらが正しいかを決めようとすると必ず外しますし、決める必要もありません。
＋で欄を増やして両方入れておけば、どちらで打っても当たります（1つのタグに5つまで）。
並べ替えは「複合語は音読みどうし・訓読みどうしで揃う」「送り仮名が付く漢字は訓読み」
という2つの規則だけで、**当てにいっていません**。選ぶのは人なので、正解が5件の
どこかにあれば足ります。測定では14語中13語が候補に入りました
（`packages/search-core/test/readingCandidates.test.ts`）。
漢字の読みの表は `packages/search-core/src/kanjiReadings.ts` にあり、
載っていない漢字が混ざる語では候補を出しません。

形態素解析器の読みは、音読み訓読みの揺れや連濁で外すことがあります。読みは
「れいぞうこ」→ #冷蔵庫 の別名になるので、間違ったまま効かせると検索に嘘が混ざります。
精度は CI で毎回測っていて、数字は実行の注記に出ます（kuromoji の仕事の
「タグの読みの精度」）。見出しと読みが同じ語（カタカナ語）だけは、確かめずに入ります。

止まっても次の晩にやり直せます（取り返しのつかない操作はしません）。

## 5. 運用で必ず決めておくこと

1. **バックアップ**。RDS なら自動バックアップを7日以上。自前なら `pg_dump` を毎晩どこかに。
   **戻せることを一度試してください**。試していないバックアップは無いのと同じです。
2. **写真の置き場所**。サーバーのディスクに置くなら、そのディスクもバックアップの対象に入れます。
3. **招待の運用**。招待リンクは1回限り・72時間ですが、作った人が誰かに見せれば誰でも入れます。
   辞めた人の端末は「承認・管理 → スタッフ」から無効にしてください。すぐに使えなくなります。
4. **ログと監視**。ログは標準出力に1行1件の JSON で出ます。CloudWatch などに流しておくと後で追えます。
   `/metrics`（Prometheus 形式）を取り込み、`ALERT_WEBHOOK_URL` に Slack の Incoming Webhook を入れておくと、
   サーバー側のエラーが出たときに気づけます。`METRICS_TOKEN` は本番では必ず設定してください（未設定だと `/metrics` は 404 になります）。

## 6. 入れ替えのときの注意

**検索語の畳み方を変えたときは、索引を作り直してください。**
索引側と検索側は同じ関数（`foldTerm`）を通す前提で、片方だけ古いままだと
入っているはずのナレッジが当たらなくなります。

```bash
docker run --rm -e DATABASE_URL=… misenare:latest npx tsx apps/api/src/batch/nightly.ts
```

夜間バッチが索引を作り直すので、放っておいても次の晩に直りますが、
その晩までは検索結果が欠けます。入れ替えた直後に1回流してください。

## 7. まだやっていないこと

正直に書いておきます。

- **多言語**。日本語のみです。
- **表記の揺れ**。ひらがなとカタカナは自動で寄ります（てれび＝テレビ）。
  かなで漢字のタグを引くには、タグの読みを人が確かめる必要があります
  （「承認・管理 → タグの読み」。機械の案を直して登録できます）。
  **送り仮名の揺れ（取付／取り付け）は自動では寄りません**。
  タグ辞書に別名として登録してください（「承認・管理 → タグ辞書」）。
- **PDF の読み取りの精度**。文字が入っていれば読めますが、段組みや表が入り組んだものは並び順が崩れることがあります。
  写真を貼っただけの PDF（スキャン）は読めません。
- **写真の自動削除**。ナレッジを消せば写真も消えますが、古い写真の整理は手作業です。
- **画面からの監視**。`/metrics` と Webhook はありますが、ダッシュボードは用意していません（Grafana などを別に立ててください）。

## 8. 外から借りているデータ（出典とライセンス）

タグの読みの候補（「承認・管理 → タグの読み」や、タグを作ったときに出る候補）は、
**KANJIDIC2** の漢字1字ごとの読みをもとに作っています。

| | |
| --- | --- |
| 出典 | KANJIDIC2 — 電子辞書研究開発グループ (EDRDG) / James William Breen 氏 |
| 入手元 | https://www.edrdg.org/kanjidic/kanjidic2.xml.gz |
| ライセンス | Creative Commons Attribution-ShareAlike 4.0 (CC BY-SA 4.0) |
| 取り込んだもの | `packages/search-core/src/kanjiReadings.generated.ts`（機械生成・手で直さない） |
| 作る台本 | `tools/gen-kanji-readings.mjs` |
| 取り直し | `.github/workflows/kanji-readings.yml`（毎月1日） |

守らないといけないことが3つあります。**商売に使うことへの制限はありません**が、
次は満たし続ける必要があります。

1. **出典を示す。** 画面の下（`apps/web/public/index.html` の `.credits`）と、
   生成ファイルの冒頭に書いてあります。消さないでください。
2. **生成ファイルは CC BY-SA 4.0 で配る。** 同じ条件で配ることが条件（ShareAlike）なので、
   派生物を1ファイルに閉じ込めてあります。**この条件はそのファイルにだけ及び、
   ミセナレ本体のソースを公開する義務はありません。**
3. **定期的に更新する。** 月1回の取り直しがそれです。止めないでください。

出典を替えたいときは `tools/gen-kanji-readings.mjs` だけを差し替えます（出力の形は変えない）。
たとえば常用漢字表は内閣告示なのでパブリックドメインですが、常用外（梱包の「梱」など）が
落ちるので、売場の言葉には足りません。いまは JIS X 0208 の漢字を採っています。

## 9. 会社のアカウントで入る（SSO）

本部の情報システム部が求める入口です。使うには環境変数を1つ決めます。

| 変数 | 例 | 説明 |
| --- | --- | --- |
| `SSO_REDIRECT_URI` | `https://misenare.example.com/api/auth/sso/callback` | 相手の IdP に登録する戻り先。**1文字でも違うと弾かれます** |

決めていなければ、SSO の経路は 404 を返します（招待QRとパスキーだけが動きます）。

会社ごとの設定は本部の管理者が入れます（`POST /api/sso/providers`）。相手に用意してもらうのは
**発行元（issuer）と client_id、必要なら client_secret** だけです。残りは相手が公開している
設定（`/.well-known/openid-configuration`）から取ります。登録項目を増やすほど、
情報システム部との往復が増えて導入が止まるためです。

```json
{
  "issuer": "https://login.microsoftonline.com/<テナントID>/v2.0",
  "clientId": "...",
  "clientSecret": "...",
  "domains": ["kdenki.example.co.jp"],
  "jitEnabled": false
}
```

`domains` は、打たれたメールアドレスから会社を決めるために使います。入口で
「どの会社ですか」と選ばせないためです。ドメインは世界で1社にしか割り当てられません。

### 初めて入ってきた人の扱い

既定は **`jitEnabled: false`（自動で作らない）** です。このとき、登録済みでない人は
**利用の申請**になります。行き止まりにはしません。

1. 相手の IdP で入れた人が、登録が無いので弾かれる
2. 「利用の申請を出しました。店長が承認すると使えるようになります」と出る
3. 店長か本部が「承認・管理 → 利用の申請」で見て、名前と配属先を決めて承認する
4. 次に入ると、使えるようになっている

申請に載るのは、**署名を通り、確認済みの会社メールアドレスを持ち、登録済みのドメインに
属する人**だけです。つまり「その会社の人であることは確かだが、こちらに登録がない」人です。

承認のときに**名前を直せます**。相手の IdP が名乗った名前をそのまま使うと、
既存の人に似せた名前が一覧に並ぶおそれがあるためです。すでに同じ名前の人がいる場合は、
申請の一覧でその場で知らせます。

断った申請は消さずに残します。同じ人が入り直しても、また一覧に出ることはありません
（「この申請は断られています」と出ます）。待っている申請は1社500件までです。

`jitEnabled: true` にすると、申請を挟まず初回に利用者を作ります。そのときは
`defaultStoreId`（配属先）が必須で、権限は `defaultTrust`（既定 `visitor`＝投稿は承認を通す）
になります。情報システム部が「承認の手間を省きたい」と言う場合の選択肢です。

どちらの場合も、**ID トークンのメールアドレスのドメインが `domains` に無ければ通しません**。
入口で打つアドレスは手がかりにすぎず、誰かを決めるのは ID トークンの中身です。

### ドメインの持ち主であることを確かめる（必須）

入口は「打たれたメールアドレスのドメイン」で会社を決めます。ドメインは世界で1社にしか
割り当てられないので、**先に登録した会社が、そのドメインの人の行き先を決められます**。

> 会社 A が `kdenki.co.jp` を登録する → ケーズデンキの社員がアドレスを打つと、
> A の IdP の画面へ送られる → そこが本物に似せた入力欄なら、合言葉を取られる

会社を作るのは運営（自己登録ではない）ですが、複数のチェーンが同じサーバーに乗る以上、
1社の管理者が他社の経路に手を伸ばせる状態は残せません。
そこで、**DNS に印を置けたドメインだけ**が入口で使われます。

```
_misenare-verify.kdenki.example.co.jp.  TXT  "misenare-verify=<32桁の印>"
```

設定画面に置き場所と値が出るので、情報システム部に頼んでください。
置いたら「置けたか確かめる」を押します（反映に数分から数時間かかります）。
確かめるまで、そのドメインの人には「まだ用意されていません」と出ます。

### つなぎを確かめる

発行元を1文字打ち間違えても、気づくのは社員が入ろうとしたときです。
設定画面の「つなぎを確かめる」で、保存前に次を確かめられます。

1. 発行元の形（https か、? や # が付いていないか）
2. 相手に届くか（打ち間違いはここで分かる）
3. 相手が名乗る発行元が、入れた値と一致するか
4. 相手の設定が指す行き先が安全か（下の「外に取りに行くときの守り」）
5. PKCE（S256）に対応しているか
6. 署名の鍵を読めるか

**ここで分かるのは発行元までです。** `client_id` と内緒の鍵が正しいか、
相手側に戻り先が登録されているかは、**本部の方が自分で一度入ってみる**しか
確かめる方法がありません（引換券の交換は、実際に入るときにしか起きないため）。
画面にもそう書いてあります。

### 外に取りに行くときの守り（SSRF 対策）

会社アカウントでは、**相手の文書が次の行き先を決めます。**
発行元を取りに行くと、その中に `jwks_uri` と `token_endpoint` が書いてあり、
こちらはそこへ取りに行きます。ここを確かめずに従うと、こちらのサーバーが
相手の指す好きな場所へ行くことになります。

> `jwks_uri: http://169.254.169.254/latest/meta-data/iam/security-credentials/`
> → クラウドの鍵を、こちらのサーバーが読んで相手に渡してしまう

設定を入れるのは本部の管理者（身内）ですが、管理者の端末の乗っ取り・相手の IdP の
乗っ取り・複数の会社が同じサーバーに乗ること——を考えると、身内かどうかとは別に
塞ぐ必要があります。`apps/api/src/auth/safeFetch.ts` で次を全部やっています。

1. **https だけ。** `http` も `file:` も認めない
2. **名前を引いて、公開のアドレスでなければ断る**（社内・自分自身・クラウドの鍵置き場）
3. **引いたアドレスにそのままつなぐ。** つなぐ直前にもう一度名前を引かせない
   （引き直しの隙に社内のアドレスへ差し替える手口＝DNS リバインディングを止める）
4. **行き先の付け替え（リダイレクト）には従わない**（公開の URL から社内へ飛ばせるため）
5. 答えの大きさ（512KB）と時間（8秒）に上限

`fetch` ではなく `node:https` を直に使っているのは、3 のために**つなぐアドレスを
指定する**必要があるからです。試験は `apps/api/test/safeFetch.test.ts` で、
実際にサーバーを立てて「1回も届かないこと」を確かめています。

### 確かめていること

1つでも落とすと他人として入れるので、全部を確かめています。

- 署名（相手の JWKS の鍵。`alg` は**ヘッダーを信用せず**鍵の種類と突き合わせる。`none` と `HS*` は拒否）
- 発行元（iss）が登録した発行元と同じか。相手の設定が名乗る発行元も突き合わせる
- 宛先（aud）に client_id が入っているか。複数あるときは azp も見る
- 期限（exp・nbf・iat。時計のずれは60秒まで許す）
- 合言葉（nonce）がこちらの出したものと同じか
- PKCE（S256）。相手が対応していなければ断る
- 覚え（state）は1回だけ。使ったら消す
- 戻り先（`#/...`）は経路だけ。外のサイトには飛ばさない

人の見分けは **subject（sub）** で行います。メールアドレスは変わる（結婚・異動・社名変更）ので、
初回だけアドレスで既存の利用者を探して結びつけ、以後は sub で引きます。
そのときアドレスは `email_verified` が真のものだけを使います。

### 同じ名前の人の見分け

会社のアカウントで入った人の名前は、相手の IdP が名乗ったものです。
そのため「承認・管理 → スタッフ」では、名前のほかに次を出します。

- **メールアドレス**（会社のアカウントで入った人のみ）
- **「会社アカウント」の印**（名前が相手の IdP 由来であること）
- **「同名あり」の注意**（同じ店に生きている同名の人が2人以上いるとき）

名前を変えても別人にはなれません。結び付けの鍵は名前でもアドレスでもなく subject です。

### 内緒の鍵（client_secret）の置き方

**DB に入れる前に包みます**（AES-256-GCM）。鍵は環境変数（`MISENARE_SECRET_KEYS`）に置きます。

#### なぜクラウドの鍵管理（AWS KMS など）を使わないか

守りたいのは「**DB の中身だけが漏れる**」場合です。実際に起きるのはこれです。

- バックアップの置き場所を間違える
- 読み取り用の複製（レプリカ）に別の人が触れる
- 調査のために本番の DB を引いて、結果が手元に残る
- DB の台だけが乗っ取られる

このとき、鍵がアプリ側にあれば中身は読めません。

サーバーごと乗っ取られたら鍵も一緒に漏れますが、**クラウドの鍵管理を使ってもそこは
大きく変わりません**（乗っ取った人はアプリと同じ権限で鍵管理を呼べます）。
違いが出るのは「鍵そのものを持ち出せない」点だけで、そのために払うものが大きいです。

- クラウドに縛られる（1台の安いサーバーで動かす前提が崩れる）
- 呼び出しごとに料金と待ち時間がかかる
- 権限の設定を間違えると、こちらのほうが事故になりやすい

ミセナレは「月数千円で1台から始められる」ことを前提に値段を決めているので、
ここに鍵管理を必須で挟むと前提が崩れます。

**後から変えられるようにはしてあります。** 包み方を `SecretBox`（`apps/api/src/crypto/secretBox.ts`）
にまとめ、包んだ値に鍵の名前を残しているので、鍵管理を使う実装を足しても DB の形は変わりません。
大口の相手が条件にしてきたら、そこで足します。

#### 行をまたいだ貼り替えを止めている

包むときに**どの行のものかを検印に混ぜます**（会社ID＋設定ID）。
そのため、A 社の行の値を B 社の行に貼り替えても開けません。
DB に書ける人が「他社の設定を自社に持ってくる」手口を、ここで止めています。

#### 鍵の入れ替え（止めずにできる）

1. 新しい鍵を `MISENARE_SECRET_KEYS` に**足す**（古いものは残す）
2. `MISENARE_SECRET_KEY_ID` を新しい鍵に向けて、アプリを入れ替える
3. `npx tsx apps/api/src/cli/rekey.ts` を流す（`--dry-run` で下見できます）
4. 古い鍵を外して、アプリを入れ替える

はじめて鍵を決めたときも 3 を流します（それまで平の形で入っていたものが包まれます）。
何度流しても同じ結果になります。鍵を決めるまでは、これまでどおり平の形で入ります。

### まだ手を付けていないところ（正直に）

- **知らせの送り先は、本部の管理者が自由に決められます。** 外のアドレスも入れられます。
  申請者の名前とアドレスがそこに送られるので、管理者が乗っ取られると漏れます。
  ただし乗っ取られた管理者は画面でも同じものを見られるので、ここが増やす危険は小さいと
  判断しています。気になる場合は、登録済みドメインのアドレスだけに絞れます。

## 10. 知らせのメール

利用の申請が来ても、**店長がアプリを開かない日は気づけません**。
申請した人はその間ずっと入れないので、会社の窓口にメールで知らせます。

Slack などの webhook ではなくメールにしたのは、家電量販の実店舗では
Slack を使っていない会社も多く、**メールはどの会社も確実に持っている**からです。

### 送信の設定（サーバー側）

| 変数 | 例 | 説明 |
| --- | --- | --- |
| `SMTP_HOST` | `smtp.office365.com` | 相手のメールサーバー |
| `SMTP_PORT` | `587` | 既定 587（STARTTLS）。465 なら最初から TLS |
| `SMTP_USER` / `SMTP_PASS` | | 認証が要るなら |
| `MAIL_FROM` | `misenare@example.com` | 差出人。**これが無いと送りません** |
| `MAIL_REPLY_TO` | | 返信先を変えるとき |
| `SMTP_CA_FILE` | | 社内サーバーが自前の認証局を使っているとき、その証明書（PEM） |
| `SMTP_ALLOW_PLAINTEXT` | | 暗号化しないままの送信を許す。**ふつうは使わない** |

SMTP を話しているので、**会社がいま使っているメールサーバーをそのまま使えます。**
Microsoft 365・Google Workspace・Amazon SES・SendGrid はどれも SMTP の窓口を持っています。
送信業者ごとの HTTP の API に寄せると、乗り換えのたびに作り直しになるため、こうしています。

**暗号化できない相手には、既定で送りません。** 認証の合言葉と本文がそのまま流れるためです。
閉じた経路の社内サーバーだけ `SMTP_ALLOW_PLAINTEXT=1` で許してください。

### 送り先（会社ごと）

本部の管理者が「承認・管理 → 会社のアカウント → 申請が来たときの知らせ」で入れます。
会社に**1つだけ**です。複数にすると「誰が見るか」が曖昧になり、かえって誰も見なくなります。
情報システム部や人事の窓口アドレスを預かり、そこから店舗に回す形を想定しています。

空にすれば止まります。サーバー側で `SMTP_HOST` が決まっていない場合は、
画面にその旨が出ます（入れても届かないため）。

### いつ送るか

夜間バッチの中で、次のどちらかのときだけ送ります。

- 前に知らせたあとに、**新しい申請が来た**
- 待っている申請があり、前に知らせてから **7日以上たった**（念押し）

毎晩送ると、1件が1か月放置されただけで30通になります。
全部決まれば送りません。送れなかった晩は印を付けないので、次の晩に送り直します。

文面には**申請者のメールアドレスと名前**を5件まで入れます。
受け取った本部が「誰のことか」分からないと動けないためです。
宛先は会社が自分で決めた窓口で、申請者は同じ会社の人なので、ここで出しています。

## 11. 外から来るものを、どこまで信じていないか

デューデリジェンスで聞かれる項目です。経路ごとに、何を確かめているかを書きます。

### 相手の IdP（会社アカウント）

9 節の「外に取りに行くときの守り」と「確かめていること」に書いたとおりです。
**相手の文書が指す行き先を信じない**（SSRF 対策）、**署名・発行元・宛先・期限・合言葉を全部見る**、
**ドメインの持ち主であることを DNS で確かめる**、の3つが要点です。

### 資料の取り込み（PDF・Word・Excel・CSV）

取り込めるのは trusted 以上ですが、「身内しか触らない」は守りになりません
（端末が乗っ取られれば、同じ経路が台を落とす道具になります）。

| 確かめていること | これが無いと |
| --- | --- |
| ファイル全体 8MB まで | 大きなファイルで記憶を使われる |
| zip の中の1つを展開して 64MB まで | .docx 1つで台が落ちる（zip 爆弾） |
| **PDF の流れを展開して 32MB まで** | 小さな PDF で台が落ちる（zlib は約1000倍に膨らむ） |
| 展開の重ね掛けは8回まで | 同じ展開を何十回も並べて時間を使われる |
| 値の入れ子は64段まで | `[[[[[…]]]]]` で呼び出しが積み上がる |
| 下書きは200件、題は100字、本文は4000字まで | 1回の取り込みで DB が膨らむ |

PDF の展開に上限が無かったのは**後から見つけた穴**です（zip の方には前からありました）。
試験は `apps/api/test/importSafety.test.ts` で、実際に 200MB に膨らむ塊を食わせて確かめています。

### 写真

| 確かめていること | これが無いと |
| --- | --- |
| JPEG・PNG・WebP だけ（**SVG は受けない**） | SVG の中に script を書けるので、同じ出どころで開くと動く |
| 1枚 3MB・1件 8枚まで | 置き場所を埋められる |
| **中身の先頭が、申告した形式と合っているか** | 「JPEG です」と言って別のものを送れる |
| 返すときに `X-Content-Type-Options: nosniff` | ブラウザが中身を見て形式を決めてしまう |
| **S3 に置くときは、形式を署名に焼き込む** | 端末が `text/html` で上げて、会社のドメインの下に好きな中身を置ける |

先頭を見る確かめと、形式を署名に焼き込むのは**後から足したもの**です。
S3 の構成では中身がサーバーを通らないので、先頭を見ることができません。
署名に焼き込むことで、違う形式で送られたリクエストは S3 側で弾かれます。

あわせて、バケットは**公開しない**設定にしてください（読むのは署名付きURL経由です）。
`PHOTO_ORIGIN` を使う場合は、**アプリと同じドメインの下に置かない**ことをおすすめします。

### バーコード

**外には問い合わせていません。** 読み取った JAN は、自社の DB の商品だけを引きます。
JAN の形（桁数と検査数字）を確かめてから引いています。

将来、外の商品データベースに問い合わせるようにする場合は、
`apps/api/src/auth/safeFetch.ts` を通してください（行き先を相手に決めさせないため）。

### 外部の候補提供元（夜間バッチ）

同義語の候補を出す仕組み（Sudachi の同義語辞書など）が返したタグの ID は、
**渡したタグの中のものだけを受けます**。行レベルセキュリティは会社IDしか見ないので、
他社のタグの ID を返されると「自社の行から他社のタグを指す」関係ができてしまいます。

## 12. 1台で動かす（本番のつもりで試す）

お金をかけずに、本番と同じ形（HTTPS・夜間バッチ・外に出す口は443だけ）で動かすための一式が
`deploy/` にあります。手元で動かすだけの `docker-compose.yml`（リポジトリの直下）とは別物です。

| ファイル | 役割 |
| --- | --- |
| `deploy/docker-compose.yml` | PostgreSQL + アプリ + Caddy + 夜間バッチ |
| `deploy/Caddyfile` | HTTPS の証明書を自動で取る。アプリへ中継する |
| `deploy/init/01-app-role.sh` | **RLS を素通りしない**アプリ用ロールを作る（下の注意） |
| `deploy/.env.example` | 書き写して `.env` にする |
| `deploy/setup.sh` | 新しいサーバー1台に、動く状態まで一気に持っていく（12-5） |

```
[スマホ] --443--> [Caddy] --内側だけ--> [アプリ:8787] --内側だけ--> [PostgreSQL:5432]
                                              └─ 写真は photos ボリューム
                                        [バッチ] 1日1回 18:30 UTC（＝日本時間 翌 3:30）
```

**アプリとデータベースの口は外に出していません**（`expose` だけで `ports` を書いていない）。
外から触れるのは Caddy の 80/443 だけです。

### 12-1. ロールの注意（ここで一度つまずきました）

PostgreSQL の公式イメージは `POSTGRES_USER` を**スーパーユーザー**として作ります。
スーパーユーザーは行レベルセキュリティを素通りするので、
**その接続で起動しようとするとアプリが起動を拒否します**（`apps/api/src/db/safety.ts`）。

```
Error: 接続ロール "misenare" はスーパーユーザーか BYPASSRLS を持っているため、
行レベルセキュリティが効きません。NOSUPERUSER NOBYPASSRLS の一般ロールで接続してください。
```

そのため、管理用（`postgres`）とアプリ用（`misenare`）を分け、
アプリ用は `deploy/init/01-app-role.sh` が `NOSUPERUSER NOBYPASSRLS` で作ります。
**この拒否は正しい動作です。**「とりあえず動かす」ために
`BYPASSRLS` を付けたり、`postgres` でつないだりしないでください。会社の壁がなくなります。

### 12-2. 手順（手で1つずつやる場合）

Ubuntu の新しい台に置くだけなら、**`deploy/setup.sh` が下の1〜5をまとめてやります**（12-5）。
ここは、何が起きているかを知りたいとき、または別の OS に置くときのために残しています。


0. **ドメインを決めて、A レコードをサーバーの IP に向ける。**（12-3 を先に読んでください）
1. `cp deploy/.env.example deploy/.env` して、`MISENARE_HOST` などを埋める。
   パスワードは `openssl rand -base64 24`、鍵は `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`。
2. `cd deploy && docker compose up -d db` → `docker compose logs -f db` で初期化の終わりを待つ。
3. `docker compose run --rm api npx tsx apps/api/src/cli/migrate.ts`
4. `docker compose run --rm api npx tsx apps/api/src/cli/bootstrap.ts "会社名" "店舗名" "あなたの名前"`
   → 出てきた招待URLを**手元に残す**（最初の管理者はこれでしか入れません）。
5. `docker compose up -d` → `https://<MISENARE_HOST>/health` が `ok` を返せば完了。

起動のときに、足りない設定の一覧が記録に出ます（`apps/api/src/config.ts`）。
`[設定]` で始まる行は読んでおいてください。致命的なものは起動を止めます。

### 12-3. ホスト名の決め方（**あとから変えられません**）

**決めたこと（2026-10-27）**

| | |
| --- | --- |
| 取るドメイン | `misenare.com` |
| アプリを置く場所 | **`app.misenare.com`**（`MISENARE_HOST` / `WEBAUTHN_RP_ID` もこれ） |
| `misenare.com` のほう | 紹介サイト・営業資料（後で作る。別のホスティングに置ける） |

会社名ではなくプロダクト名にしたのは、会社名はまだ決まっていないこと、法人を作る前でも
個人で取れること、そして**売るときに渡すのはプロダクトなので `misenare.com` が資産になる**ためです。
会社名のドメインにアプリを載せると「会社は残してサービスだけ渡す」ができなくなります。

アプリをサブドメイン（`app.`）に置いたのは、`WEBAUTHN_RP_ID` を `misenare.com` にすると
**そのドメインのどのサブドメインでもパスキーが使えてしまう**ためです。
後から紹介サイトを外部のサービスに置いたとき、そこがアプリと同じ鍵の範囲に入ります。


`WEBAUTHN_RP_ID` はパスキーの「どのサイトの鍵か」を決める値で、**ホスト名そのもの**です。

- **ホスト名を変えると、登録済みのパスキーは全部使えなくなります。** 作り直しになります。
- なので、試すだけの環境でも「本番でも使うドメイン」で始めるのが安全です。
  本番で `misenare.example.com` にする予定なら、試す段階から
  `test.misenare.example.com` ではなく `misenare.example.com` のサブドメインの決め方を先に決めてください。
- サブドメインをまたいで使いたい場合だけ、`WEBAUTHN_RP_ID` を親ドメイン（`example.com`）にします。
  親にすると、そのドメインの**どのサブドメインでも**その鍵が使えてしまう点に注意してください。

**無料のダイナミックDNS（`*.duckdns.org` など）を使うときの制限**：

| | 動くか |
| --- | --- |
| 招待QRで入る | 動く |
| パスキー | 動く（ただし、あとで本番ドメインに移ると作り直し） |
| 会社のアカウント（SSO） | **会社ドメインの確認ができません** |

SSO は「その会社が本当にそのドメインの持ち主か」を
`_misenare-verify.<会社のドメイン>` の TXT レコードで確かめます（§9）。
これは**会社側のドメイン**に置くものなので、ミセナレ側のホスト名が何であっても確かめ自体は動きます。
ただし自分でひと通り試すときは、TXT を置ける本物のドメインが片方に必要です。

### 12-4. 無料枠で試す場合

常時動かせて無料のものは、いまのところ Oracle Cloud の Always Free（ARM）だけです。
次を確かめてあります。

- **自動で課金されることはありません。** Always Free のままなら、カード登録だけで引き落とされません。
  有料に切り替える操作をしない限り、超えた分は請求ではなく**停止**になります。
- ただし **ARM（A1）は「在庫切れ」で作れないことがよくあります**（`Out of host capacity`）。
  これは選んだ地域の空き次第で、大阪は区画が1つしかないため特に出やすいです。時間を変えて試すほかありません。
- **2 OCPU / 12GB を超える A1 を無料枠で作ると、30日後に消されます。**
  無料枠の上限（合計 4 OCPU / 24GB）の内側に収めてください。1台構成なら 2 OCPU / 12GB で足ります。

容量の目安（1台・2 OCPU / 12GB）：
PostgreSQL と アプリと Caddy を同じ台に置いても、
数十店舗・ナレッジ数万件までは余ります。写真の置き場所（ディスク）のほうが先に埋まります。

### 12-5. Oracle Cloud に置く（実際の手順）

**この順番でないと、証明書の取得で必ず失敗します。**
Caddy は Let's Encrypt に「このドメインの持ち主だ」と示すために 80 番で応答する必要があるので、
**先に入口が開いていて、ドメインがこの台を指している**状態を作ってから起動します。

| 順 | すること | 場所 |
| --- | --- | --- |
| 1 | `misenare.com` を取る | ドメインの販売サイト |
| 2 | Always Free のインスタンスを作る（下の設定） | Oracle の画面 |
| 3 | **VCN のセキュリティリストで 80 と 443 を開ける** | Oracle の画面 |
| 4 | `app.misenare.com` の A レコードを、この台の公開 IP に向ける | ドメインの DNS |
| 5 | `dig app.misenare.com` で IP が返るのを待つ（数分〜数時間） | 手元 |
| 6 | `setup.sh` を動かす | サーバーに ssh して |
| 7 | 最初の管理者を作る | 同じ |

**2 のインスタンスの設定**

| 項目 | 値 | 理由 |
| --- | --- | --- |
| シェイプ | VM.Standard.A1.Flex | Always Free の対象はこれ（ARM） |
| OCPU / メモリ | **2 OCPU / 12GB** | 無料枠の上限（4/24）の内側。超えると30日で消される |
| イメージ | Ubuntu 24.04 | `setup.sh` がこれを前提にしている |
| ブートボリューム | 50GB〜100GB | 無料枠は合計200GBまで。写真の置き場所になる |
| 公開 IP | 割り当てる | 無いと外から繋がらない |

**ssh の鍵は作るときにしか受け取れません。** 落としたファイルを失くすと入れなくなります。

**6 の中身**

```bash
curl -fsSL https://raw.githubusercontent.com/Yukisiooisiiyo/misenare/main/deploy/setup.sh -o setup.sh
less setup.sh                                  # 何をするか読んでから
sudo bash setup.sh app.misenare.com
```

`setup.sh` がやること：Docker を入れる → **この台の 80 と 443 を開ける** →
ソースを置く（`/opt/misenare`）→ 合言葉と鍵を**この台で作って** `.env` に書く →
イメージを作る → 表を作る → 起動する。
合言葉は画面にも記録にも出しません（`/opt/misenare/deploy/.env` だけに入ります）。

**3 と 2 の違いに注意**：Oracle の Ubuntu イメージは、22 番以外を拒否する規則が
**台の中にも**最初から入っています。クラウド側（3）だけ開けても届きません。
`setup.sh` が台の中のほうを開けますが、**クラウド側は画面から手で開ける必要があります**。

**7 の中身**

```bash
cd /opt/misenare/deploy
docker compose run --rm api npx tsx apps/api/src/cli/bootstrap.ts "会社名" "店舗名" "あなたの名前"
```

出てくる招待URLは**その場で開いてください**。最初の管理者はこれでしか入れません。

**確かめ方**

```bash
curl -i https://app.misenare.com/health         # ok が返れば完了
docker compose logs caddy --tail 50             # 証明書が取れないとき
docker compose logs api --tail 50               # 起動しないとき（[設定] の行を読む）
```

起動のときに出る `△` の行は、1台で試す段では出て当然のものです
（写真がこの台のディスクにある／エラーの知らせ先が無い／メールを送れない）。
`×` の行があるときだけ起動が止まります。

### 12-6. 無料枠で動かすときの手加減

- **`TOKENIZER=kuromoji` を入れない。** 記憶を数百MB使います。12GB あるので動きはしますが、
  検索の当たりの差より、まず動かすことを優先してください（後から足せます）。
- **バックアップは自分で取る。** 無料枠には自動バックアップが付きません。
  `docker compose exec -T db pg_dump -U postgres misenare | gzip > ~/misenare-$(date +%F).sql.gz`
  を cron に入れ、**別の場所に持ち出してください**（同じ台に置くと、台が消えたときに一緒に消えます）。
- **止まっても気づけない。** 無料枠は落ちることがあります。本番で使うなら、
  外から `/health` を叩いて知らせる仕組み（UptimeRobot などの無料枠）を別に用意してください。
